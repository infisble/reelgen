# Нотатка до тестового: AI Engineer, HOLYWATER

## Частина 1. Вибір стеку

> Схема етапів і артефактів — у Частині 2.

**Чому workflow, а не агент.** У нас систематичні дії, і для них workflow кращий за агента: агент певною
мірою непередбачуваний, і це може бути проблемою.

**Чому свій раннер, а не n8n / low-code.** Нам важливі оркестрація і трейсинг. Low-code структури менш
масштабовані й гірше працюють з великими даними для перевірки помилок, тому краще реалізувати це кодом.

| Шар | Обрав | Відкинув / відклав | Чому |
|---|---|---|---|
| Оркестрація | PoC: свій раннер. Прод: **Temporal** | n8n та інші low-code | Оркестрація і трейсинг; low-code гірше масштабується і гірше працює з даними для перевірок |
| Сценарій (LLM) | **OpenAI** | — | Можна одразу протестувати |
| Голос | PoC: OpenAI TTS. Прод: **ElevenLabs** | — | ElevenLabs кращий для серіалу, але на тестове не було токенів, тому OpenAI |
| Відео | **Veo 3** | — | Мені ближчий, я вже з ним працював, є досвід |
| Монтаж | PoC: ffmpeg. Прод: **Remotion** | — | Remotion кращий для титрів і графіки |
| Консистентність героя | Конкретні правила + передача контексту в кожен крок workflow | — | Щоб отримувати кращий результат |

**Ризики, які для мене найстрашніші:**
1. **Емоційність героїв і передача контексту.** Репліка може прозвучати правильно, але без потрібної емоції.
2. **Якість генерації самих героїв.** Поганий motion, дрейф персонажа між шотами.
3. **Склейки.** Невдалі вирізки, темні плями на кадрах.

## Частина 2. Дата-флоу

### Етапи і артефакти
```
idea ─► [parse] ─► [script] ─► [cast] ─► [voice] ─► [images] ─► [render] ─► [assemble] ─► [qa]
        код        LLM         image      TTS→STT    image+refs   ffmpeg      ffmpeg         probe+STT
        input.json script.json char_N.png line_N.wav shot_N.png   shot_N.mp4  final.mp4      report.json
```
| Етап | Що робить | Артефакт (ключові поля) |
|---|---|---|
| parse | Кодом витягує репліки з лапок (або бере весь текст), визначає мову, оцінює тривалість мовлення й відхиляє вхід, що не влазить у 30 с | `ParsedInput{lines[], lines_source, lang, est_speech_s}` |
| script | LLM повертає план за JSON-схемою. **Репліки лише за `line_index`**, текст реплік LLM не бачить на виході | `ScriptPlan{title, visual_style, characters[{name, appearance, voice}], shots[{shot_id, lines[{line_index, speaker, delivery}], visual_prompt, camera}]}`. `delivery` — як актор має зіграти репліку з урахуванням сцени (емоція, гучність, темп); передається в TTS як режисерська вказівка |
| (серіал) | `--series`: біблія з фіксованим кастом і стилем. Код примусово переписує вигляд і голос відомих героїв у плані: консистентність між епізодами гарантує код, а не промпт | `examples/series/*.json` |
| cast | Еталонне зображення кожного персонажа (character sheet). Далі кожен шот генерується з еталонами тих, хто в кадрі (`on_screen`), тож обличчя й одяг не «дрейфують» між шотами | `cast/char_N.png` + промпт |
| voice | TTS кожної репліки, потім STT, потім порівняння слово в слово (WER = 0) | `line_N.json{text, voice, status: verified/mismatch/unverified, attempts, check{heard, wer}}` |
| images | Кадр 2:3, потім vision-суддя (оцінка 1–5, текст/вотермарки, анатомія) | `shot_N.json{prompt, attempts, accepted, review}` |
| render | Аудіотаймлайн (пауза → репліка → пауза), Ken Burns, субтитри точно за таймінгом репліки | `render/shot_N.mp4` |
| assemble | Concat шотів | `final.mp4` |
| qa | Тривалість 8–30 с, 1080×1920, є аудіо і воно не тихе, **STT фінального файлу збігається з репліками** | `report.json{passed, checks, warnings, counters}` |

### Стан і зшивання етапів
- Один запуск = одна директорія `runs/<id>/`. Етапи спілкуються **лише через файли-контракти** (pydantic-моделі в `models.py`), а не через пам'ять процесу. Тому будь-який етап можна перезапустити окремо.
- `state.json` (атомарний запис) зберігає статус, кількість спроб, тривалість і outputs кожного етапу, а також лічильники викликів і ретраїв. `events.jsonl` — це лог рішень (що почув STT, що сказав суддя).
- `--resume` пропускає `done`-етапи. `--from-stage X` інвалідовує X і все після нього.
- Пер-айтемний кеш за хешем входів (текст + голос + модель для реплік, промпт + модель для кадрів). Повторний прогін етапу перегенеровує лише змінене.
- У проді: метадані в Postgres, медіа в S3/GCS (ключ = content hash), оркестратор із durable execution (Temporal або аналог) замість локального раннера. Контракти етапів при цьому не змінюються.

### Обробка помилок
| Що зламалось | Реакція |
|---|---|
| 429 / 5xx / таймаут API | Ретрай з exponential backoff у SDK (`max_retries=4`) |
| LLM повернув невалідний план (не та кількість шотів, пропущена репліка, неіснуючий спікер, **текст репліки в image-промпті**) | Repair loop: помилки валідатора повертаються в LLM як фідбек, до 3 спроб, далі `failed` |
| TTS «з'їв» або перекрутив слово (STT ≠ репліка) | Перегенерація **лише цієї репліки** з повільнішим темпом, до 3 спроб. Якщо не вийшло, статус `mismatch`, відео все одно збирається, а запуск отримує `needs_review` |
| Кадр забракований суддею | Перегенерація **лише цього шоту**, до 2 спроб, далі береться найкращий з `accepted=false` → `needs_review`. Падіння самого судді не блокує запуск |
| Таймлайн > 30 с | `failed` на render. Вхід, що свідомо не влазить, відсікається ще на parse |
| Краш процесу посеред запуску | `--resume`: продовжує з етапу, що впав. (Реально сталося під час eval-прогону: Windows тримав lock на `state.json`. Додав ретрай на запис, а запуск дорозібрався через resume) |

### Human-in-the-loop
- **Є:** статус `needs_review` (exit code 2) з причиною в `report.json`. Людина дивиться лише на ті запуски, де автоматика не впевнена (розбіжність STT, слабкий кадр).
- **Свідомо немає** між етапами в happy path: мета — автономність. У проді додав би опційний approve-гейт після `script` (дешевий етап, дорогі ще попереду) для серій/персонажів, які йдуть у релиз.
- **Рівень автономності як налаштування, а не константа** (ідея «autonomy slider» Карпатого). Для нової серії вмикаємо approve сценарію й кадрів героя. Коли eval показує стабільність, approve вимикаємо і лишаємо лише `needs_review`. Перемикач живе в конфігу серії, код пайплайну не змінюється.
- **Перевірка людиною має бути швидкою.** Поверх `report.json` потрібен review-екран: кадри шотів, програвач, почутий STT текст поруч з очікуваним і кнопки approve / перегенерувати шот / перегенерувати репліку. Кнопки відповідають уже наявному `--from-stage` і кешу, тож нічого перегенеровувати повністю не треба.

## Частина 3. Метрики та оцінка якості

**Технічні (є в `state.json` / `evals`):** success rate, `needs_review` rate, failure rate за етапами;
wall time на запуск і на етап; кількість ретраїв (script repairs, TTS, image) на запуск; виклики й токени провайдерів (основа для cost per video).

**Якість контенту:**
| Автоматизовано | Як |
|---|---|
| Дослівність репліки | STT фінального файлу, WER = 0 (hard gate) |
| Технічна валідність | Тривалість, роздільність, аудіо є і не тихе |
| Відповідність кадру промпту, артефакти | Vision LLM-суддя, оцінка 1–5 + прапори |
| Структура сценарію | Детермінований валідатор |
| *Далі:* консистентність персонажа між шотами | Face/CLIP embeddings similarity |
| *Далі:* синхрон субтитрів/губ | Forced alignment, SyncNet-подібні метрики |

**Ручне:** чи «чіпляє» історія, акторська подача голосу, естетика, ритм монтажу. Тут парні порівняння (A/B двох версій пайплайну на одній ідеї) замість абсолютних оцінок. Їх легше робити послідовно, а потім частину можна відкалібрувати під LLM-суддю.

**Eval-процес (каркас уже є, `reelgen/evals.py`):**
0. Почати з аналізу помилок, а не з метрик (підхід Хамела Хусейна): переглянути 50–100 реальних відео, розкласти браки на категорії (дрейф героя, неприродна інтонація, текст на кадрі, «не та» емоція) і автоматизувати перевірки для найчастіших. Метрики, які ніхто не підкріпив переглядом даних, міряють не те.
1. Фіксований набір ідей `evals/ideas.jsonl` покриває складні випадки: українська, 2 репліки, без лапок, числа й імена, апострофи та пунктуація.
2. `evals run --label <версія>` дає JSON з агрегатами й метриками кожного кейсу.
3. `evals compare a.json b.json` показує дельту агрегатів і підсвічує кейси, що змінились.
4. Правило в `CLAUDE.md`: зміна промптів або моделей не мержиться, якщо падає `success_rate` чи `verbatim_pass_rate`.

**Перший тиждень:** аналіз помилок на перших 50 відео, все вище, плюс розширити набір до 30–50 ідей, cost per video, нічний регресійний прогін, щотижнева ручна A/B-сесія на 10 відео.
**Колись потім:** консистентність персонажа за embeddings, ліпсинк-метрики, залучення глядачів (retention) як north star, калібрування LLM-судді на ручних оцінках, дашборд трендів.

## Частина 5. Як я працював з AI

**Інструмент:** Claude Code (агент у VS Code). Я поставив задачу (PDF тестового), вибрав провайдерів
і розподіл роботи (Частину 1 пишу сам). Агент спроєктував і написав код, тести й harness.
Експорт чату: [docs/chat-export.md](docs/chat-export.md).

**Як будувалися промпти і structured output:**
- Головне рішення: **не довіряти LLM дослівність**. Схема `ScriptPlan` не має поля для тексту реплік, тільки `line_index`. Текст підставляє код. Тому парафраз неможливий конструктивно, а не «за проханням у промпті».
- Вихід LLM обмежений `Literal`-енумами (голоси, рух камери). Валідатор перевіряє решту, а його помилки повертаються в промпт як фідбек.
- STT працює без підказки очікуваного тексту (`prompt`). Інакше він би «чув» те, що ми хочемо.

**Harness для агентів (щоб доводили задачу до кінця без мене):** `CLAUDE.md` задає інваріанти й порядок дій. `scripts/check.py` (ruff + format + 20 тестів, усі офлайн) — єдине визначення «готово». Stop-hook у `.claude/settings.json` не дає агенту завершитись, поки чек червоний. Тести на провайдери OpenAI ганяють реальний код через mock HTTP, тому ключ для CI не потрібен.

**Де AI помилився (реальні випадки з цієї сесії):**
1. Demo-шаблон сценарію вставляв репліку в image-промпт. Власний валідатор пайплайну це зловив і відхилив план з першого запуску. Виправлено.
2. Перший eval-прогін впав на Windows: `os.replace(state.json)` отримав `PermissionError` через тимчасовий lock файлу. Eval-агрегатор при цьому порахував завислий `running`-запуск як «не провал». Обидва баги виправлено: ретрай атомарного запису, і все, що не `done`/`needs_review`, тепер провал.
3. Підказка `--resume` у CLI не враховувала нестандартний `--runs-dir`.
4. Demo-діалог з двох реплік озвучувався одним голосом.
5. Lint-порушення (довгі рядки), які спіймав gate. Ще кілька разів масові правки агента застосувались лише частково, бо форматер встиг змінити код, на який вони спирались. Щоразу це ловив assert у скрипті правки, а не тихий зламаний файл.
8. **Аналіз помилок на власному виході** (підхід із Частини 3). Автоматичний прогін `--writer claude` пройшов усі гейти, але покадровий перегляд показав 3 баги, яких QA не бачить: кухня стала городом (ключове слово `field` спрацювало на «depth of field»), огірок став капустою (шаблону не було, і Claude чесно написав «cabbage template styled as a cucumber»), ведучий отримав рожевий бантик замість метелика («bow tie» → «bow»). Виправлено, додано регресійні тести, рендер перезапущено з етапу `cast` без нового виклику LLM. Висновок: технічні гейти доводять, що відео валідне, але не що воно правильне. Звідси рішення в Частині 3 починати з перегляду даних.
9. **Локальна 3D-генерація без ключів** (DreamShaper XL Turbo на RTX 4060, ~12 с на кадр). Перший прогін дав
   Pixar-рівень, але покадровий перегляд знайшов 3 проблеми, і кожна стала правилом системи. (а) У серії 3
   Claude вставив у кадр опис «бідного» кабачка, і корона зникла. Тепер зовнішність героя в промпт кадру
   вставляє код з біблії серіалу, а LLM описує лише дію й місце. (б) Емоцію модель ігнорує, якщо вона в кінці
   промпту. Тепер є окреме поле `expression`, і воно йде першим. (в) Модель домалювала помідору другу пару очей.
   Тепер є vision-суддя без ключів через Claude Code, він бракує кадр, і перегенерується лише цей кадр. Окремо
   знайшовся баг у фолбеку: при однакових оцінках обирався кадр з дефектом. Виправлено, дефект коштує більше за
   бал відповідності.
   **Чесне обмеження:** Turbo-модель погано керує емоцією («шок» малює усмішкою). Такі запуски завершуються
   `needs_review` і йдуть людині.
7. Перший рендер ляльок упав: при сердитому обличчі й ледь відкритому роті еліпс рота отримував від'ємну висоту. Виправлено, а запуск продовжився через `--resume` з етапу `render`, без повторної озвучки.
6. Агент виставив дефолтні моделі зі своїх знань: `gpt-image-1` і `gpt-4o-transcribe` виявились deprecated, а в першій версії Частини 1 Sora фігурувала як варіант, хоча її API вже вимкнено. Знайшлося, коли я попросив звірити стек з актуальною документацією. Виправлено на `gpt-image-2.5-flare` / `gpt-transcribe`. Висновок: знання моделі застарівають, тож факти про API треба перевіряти по документації. OpenAI-шлях досі перевірено лише через mock HTTP: **це головний неперевірений ризик**.

**Моя рефлексія:**
- Модель роботи: я ставлю задачу, ухвалюю рішення і рев'юю, а агент виконує. Ключові рішення були мої: OpenAI як єдиний провайдер плюс demo-режим без ключа, щоб пайплайн можна було перевірити одразу. Агент запропонував контракт «репліка лише за індексом», і я його залишив, бо він розв'язує вимогу дослівності конструктивно.
- Код руками не переписував, і це свідомо: кожне виправлення йшло через агента і проходило той самий gate (`scripts/check.py`). Це і є перевірка того, що harness працює: баги з пунктів 1–5 вище зловили валідатор, eval-прогін і лінтер, а не я очима.
- Чого AI не зробить за мене: перевірки на живих API (пункт 6), смакової оцінки відео й вибору моделей під наш контент. Для цього потрібні ключі, eval-набір і людські A/B.
- **Прозорість:** Частину 1 я надиктував в інтерв'ю з агентом. Рішення й аргументи мої. Агент поставив запитання, переклав мої відповіді українською й розклав їх у таблицю. Окремо агент зробив для мене довідку з альтернативами та актуальними API, з якої я обирав.
